孚盟是我们公司每天用的客户管理系统。它的网页端只适合真人操作：多账号、钉钉扫码登录、会话会掉、没有 SDK、请求还要控制频率。我白天用它查客户、看公海、做查重、查海关数据；到了晚上就想，这些重复动作能不能让脚本和 Agent 替我做。

## 问题

网页端的每个动作都绑在一个浏览器会话上。直接用脚本请求接口，登录态很快就掉；多个脚本共用账号，又会互相抢会话。业务上还卡着几条硬规则：领取公海前必须先查重、释放后有 3 天冷却、客户容量有上限。这些规则如果只写在人的脑子里，早晚会出错。

## 做法

fuma-platform 是一个常驻本地的 Node 服务，不重写孚盟的业务逻辑，只做它外面的一层薄封装。43 项能力只在注册表里定义一次，再生成 CLI、REST v1（Fastify，只监听回环地址）、MCP stdio 和 SKILL 四种入口——不会出现「CLI 能做、REST 不能」的情况。

写操作先落本地 SQLite 事务加 outbox，再异步同步上游。上游如果冲突，对账程序记录差异而不是静默覆盖，所以调用方拿到的永远是确定事实。登录走钉钉 SSO 扫码，token 用 AES-256-GCM 加密落库，心跳保活，24 小时到期后进重登队列。

## 架构要点

- 会话池 + 请求池：按账号串行、QPS 限速加抖动，浏览器只在登录和刷新时拉起。
- 本地事实库 + 事件总线：写操作的真相先在本地，再慢慢同步。
- 海关缓存：强制缓存，TTL、上游更新日志失效、LRU 容量上限、权限域隔离；冷查约 1 秒，命中在 0.1 毫秒量级。
- 运维：systemd 常驻、健康检查、`.env` 与 token 权限 600。

## 学到什么

注册表才是产品。四个入口从同一份定义生成之后，维护量从四份变成一份。也学会了把限制写进 README：新增跟进的接口契约还没确认，删除客户需要测试账号没有的权限，这些都如实写清楚，比假装能用便宜得多。

53 个测试通过，MIT 开源。用下来最大的感受是：浏览器是一份你没参与设计过的契约，封装的价值在于把这份契约变成本地可验证的事实。
