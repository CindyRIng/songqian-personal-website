孚盟是我每天用来做客户的 CRM。它的网页端只适合真人操作：一个账号、一个浏览器标签页、不着急的时候——扫码、选企业、然后点。客户列表、公海、查重、海关查询这些真正有用的能力，都锁在那个网页里。

fuma-platform 是它外面的一层薄封装。它不重写孚盟的业务逻辑，也不想成为第二个 CRM，只把网页端变成一组本地、可编程、可缓存的能力，交给其他系统和 Agent 调用。

## 本地事实优先

最重要的设计规则：写操作先落本地 SQLite 事务 + outbox，再异步同步上游。上游如果冲突，对账程序记录差异而不是静默覆盖。调用方拿到的永远是本地事实，不存在半完成状态。

## 一份注册表，四种入口

核心是一份能力注册表：43 项能力只定义一次，再生成 CLI 命令、REST v1 路由（Fastify，仅回环 + Bearer）、MCP stdio 工具与 SKILL 文档。不存在「CLI 能做、REST 不能」的路径；`npm run spec` 从同一份源生成 OpenAPI、CLI 与 MCP 契约。

## 会话才是难点

销售账号背后是真人。登录是钉钉 SSO 扫码，token 用 AES-256-GCM 加密落库，心跳保活，24 小时过期进重登队列。请求池按账号串行、QPS 限速加抖动、读请求走缓存；浏览器只在登录或刷新时拉起。

## 有规则的海关缓存

海关查询上游又慢又贵，所以强制缓存：TTL、上游更新日志失效、LRU 容量上限、权限域隔离。冷查约一秒，命中在 0.1 毫秒量级。

## 学到的东西

注册表才是产品。当接口从同一份定义生成，四种入口不再是四份维护负担，而是一份。我也学会了把限制写进 README：新增跟进还卡在上游契约未确认，删除客户需要测试账号没有的权限。写下来几乎不花成本，却能省掉一轮解释。

先在这个 CRM 里处理业务，再给它写自动化，我对软件的理解变了：浏览器是一份你没参与设计过的契约。
