探迹在浏览器里很强，在程序里很难：登录依赖 SSO cookie，频繁请求会触发限频，页面接口会变，多个脚本共用一个账号还会互相抢浏览器 profile。

## 问题

探迹是按额度计费的。查企业、看工商、股东、主要人员，解锁联系方式都要花额度。手工在网页里查又慢又容易把额度花在无效客户上。我需要一个能缓存、能限频、能被 Agent 调用的本地接口，同时不要把账号搞挂。

## 做法

tanji-client 把这些问题收敛成一个本地 owner 进程：一个浏览器、一个 REST 服务、一套缓存和限频。其他进程（CLI、MCP、脚本）只通过本地 REST 调用，不会各自去开浏览器。

多账号：每个账号独立 profile、缓存和端口。MCP 默认只代理到 REST，不持有 profile，所以「already running」的锁问题消失。

## 架构要点

- 筛选是数据不是表单：12 个类别、345 条高级筛选条件做成注册表，接受筛选文件，高级筛选于是变成数据问题。
- 限频是产品设计：企业详情支持轻量模式（只取基础与详情段）省调用；解锁默认只打 1 个上游调用；限频分 priority（解锁、登录）和 bulk（批量读）两条通道，长批处理不会堵住解锁。
- 缓存：cache-aside + TTL，命中约 1–2ms，另有清理命令，需要真相时用。
- 登录：处理「账号中心还登录、sales 会话失效」的中间态，验证码走可见浏览器兜底。
- 运维：systemd 常驻、多账号启动、日志轮转、健康检查。

## 学到什么

多账号系统首先是隔离问题，其次才是功能问题。限频应该和 API 一起设计，而不是等第一个账号被限之后再补。

还有一点是诚实：README 里写清楚真实限制——缓存没有 LRU、部分缓存 key 没纳入排序、解锁会消耗额度所以必须显式确认。写出来之后，用的人反而更放心。
