招聘数据只解决一半问题。一串职位告诉你这家公司在招人，但不告诉你它是不是真公司、有多大、谁在管。真正有用的链路是：关键词加城市 → 职位 → 去重后的公司 → 工商信息 → 再看这家公司的其他职位。在浏览器里手工做这件事就是数据录入；用脚本做，需要一条不会断的会话。

zhilian-client 是这个小型家族里的第二个客户端，我刻意照着第一个的样子做。它把智联招聘的 Web 产品变成常驻本地的只读服务，17 个操作以四种形态暴露：CLI、REST（回环 + Bearer、OpenAPI 与自包含文档）、17 个工具的 MCP stdio，以及 SKILL 工作流。

## 链路本身就是产品

操作是围绕调研回路设计的，而不是围绕网站：按关键词与城市搜职位；用 `queryId` 翻页；取职位详情；从一次查询里列出不重复的公司；取公司详情（含工商信息）；取这家公司的全部在招职位。最后一项在上游是分页的，很容易被截断——这个客户端把它取全（真实测试里是 21/21），而不是悄悄只返回第一页。

## 复用是一种策略

做完 boss-client 之后，我有了一个被验证过的形状：单一 owner 进程、cloak 浏览器会话、处理页面内 fetch 与 DOM 提取的适配层、zod 领域模型、四份契约的生成器、带 TTL 的 SQLite cache-aside、systemd unit。做第二个客户端基本是替换，而不是再发明一次。这正是重点：不能复用的架构，就是不能信任的架构。

## 缓存与反爬的现实

搜索与公司详情缓存 2 小时到 7 天，支持强制刷新，只存结构化字段——不存 HTML、不存 cookie、不存验证码产物。会话 token 自动续期（access 约 7 天，refresh 约 30 天）。EdgeOne 的人机验证用中继处理：服务可以自动点击，也可以返回带坐标的截图，交给人或 Agent 去解。

## 学到的东西

设计的成色在第二次实现里才被检验。因为第一个客户端已经划好了接缝，我可以在不碰架构的前提下换一个上游、换一套分页、换一个反爬故事。35 个单测与生成式契约让四个入口保持诚实；只读与最小化采集也不只是合规备注，它们让这个东西足够无聊，可以一直无人值守地跑着。
